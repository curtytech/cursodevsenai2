🍽️ 1. O QUE É UMA API? (A ANALOGIA DO GARÇOM)

          

            Imagine que você foi jantar em um restaurante:
          

          

            • Você (Cliente / Navegador): Senta na mesa e quer comer.

            • A Cozinha (Servidor / Banco de Dados): Onde os alimentos ficam guardados e a comida é preparada. Você não pode entrar lá para mexer nos fogões por motivos de segurança.

            • O Garçom (A API): É a ponte! Você diz o que quer, ele anota na comanda, leva até a cozinha e traz o prato pronto para você.
          

        


        

          
🍔 2. POR QUE O GRAPHQL FOI CRIADO? (REST VS GRAPHQL)

          

            No modelo tradicional (chamado REST), os pratos são do tipo "Prato Feito" (Combo fechado). Você pede o Combo 1 e ele vem com arroz, feijão, bife, salada e refrigerante. Se você só queria o bife, todo o restante vira comida jogada fora!
          


          

            

              
🍔 REST TRADICIONAL (PRATO PRONTO)

              
    
                
  • Over-fetching (Excesso de dados): Você pede o nome de um usuário e a API te manda 40 coisas desnecessárias (CPF, endereço, tipo sanguíneo, senhas criptografadas). Isso gasta a internet móvel do usuário!
    • 
                
  • Under-fetching (Falta de dados): Para montar a tela do perfil, você precisa chamar a API 3 vezes: uma para o usuário, outra para os pedidos e outra para os amigos.
    • 
                
  • Muitos endereços (URLs) diferentes para decorar.
    • 
              

            


            

              
🥗 GRAPHQL (SELF-SERVICE GOURMET)

              
    
                
  • Zero Desperdício: Você entrega uma lista dizendo: "Quero apenas o campo nome e a foto". O servidor só manda isso!
    • 
                
  • Tudo em 1 Viagem: Você pode pedir dados de usuários, pedidos e amigos em uma única requisição.
    • 
                
  • Geralmente tem apenas 1 endereço central (ex: /graphql) usando o método POST.
    • 
              

            

          

        


        

          
⚡ 3. COMO O JAVASCRIPT CONVERSA COM O GRAPHQL?

          

            Você não precisa de bibliotecas pesadas para começar! Um simples fetch() do JavaScript faz todo o trabalho:
          

          
// Veja como é simples no JavaScript puro:
fetch('https://countries.trevorblades.com/graphql', {
  method: 'POST', // Sempre POST
  headers: {
    'Content-Type': 'application/json'
  },
  body: JSON.stringify({
    query: `
      query {
        countries {
          name
          emoji
        }
      }
    `
  })
})
.then(resposta => resposta.json())
.then(resultado => {
  console.log("Dados recebidos da API:", resultado.data);
});

          

            Viu só? Enviamos um objeto com a propriedade query contendo o texto da nossa consulta, e o servidor responde com um JSON contendo exatamente os dados pedidos!
          

        


      

    


    
    

      

        
        

          
📖 DICIONÁRIO DOS TERMOS QUE VOCÊ PRECISA SABER

          
          
1. Query (Consulta)

          
É a operação para buscar ou ler dados. Ela nunca altera nada no servidor (equivale ao GET do REST).


          
2. Mutation (Mutação)

          
É a operação para gravar, alterar ou apagar dados (como cadastrar um novo aluno ou curtir uma foto). Equivale ao POST, PUT ou DELETE.


          
3. Subscription (Assinatura em Tempo Real)

          
É como uma ligação contínua. Quando algo novo acontece no servidor (ex: uma nova mensagem no chat), o servidor envia a novidade na hora para a sua tela.


          
4. Variables (Variáveis)

          
Parâmetros dinâmicos que passamos para a consulta sem precisar colar texto dentro da query. No nosso laboratório, você viu o $codigo: ID! sendo preenchido por { "codigo": "BR" }.


          
5. Schema (O Contrato de Dados)

          
É o manual de regras do servidor. Ele define com rigor quais tipos de dados existem (Texto, Número, Booleano) para evitar que o cliente peça campos inventados.

DESAFIO 1: O QUE É OVER-FETCHING?

              

                Seu aplicativo de celular só precisa mostrar o nome e a foto de um usuário na barra do topo. A API REST tradicional te entrega 50 campos, incluindo histórico médico e endereço completo. Qual o nome desse problema e como o GraphQL resolve?
              

              
              

RESPOSTA DO PROFESSOR:
Esse problema se chama OVER-FETCHING (receber mais dados do que o necessário).
O GraphQL resolve isso permitindo que o cliente escreva na consulta apenas:
query {
  usuario {
    nome
    foto
  }
}
O servidor lê seu pedido e manda rigorosamente só esses dois campos, deixando a página leve e economizando o plano de internet do usuário!
              

            


            

              
DESAFIO 2: QUERY OU MUTATION?

              

                Você está criando uma loja virtual. O usuário clica no botão "Finalizar Compra". Você deve usar uma QUERY ou uma MUTATION para essa ação?
              

              
              

RESPOSTA DO PROFESSOR:
Você deve usar uma MUTATION!
Porque finalizar uma compra altera o estado do sistema (cria um novo pedido no banco de dados e dá baixa no estoque).
Lembre-se:
• Para LER dados = Query
• Para GRAVAR, ALTERAR ou DELETAR = Mutation
              

            


            

              
DESAFIO 3: POR QUE O MÉTODO É POST?

              

                Se uma Query serve apenas para "buscar" dados, por que a requisição HTTP enviada pelo JavaScript é do tipo POST e não GET?
              

              
              

RESPOSTA DO PROFESSOR:
Porque consultas GraphQL podem ser longas e cheias de campos aninhados.
Se usássemos GET, a consulta inteira teria que ser colocada na URL da página, o que geraria URLs gigantescas e ultrapassaria o limite máximo de tamanho de links permitido pelos navegadores.
Com o método POST, a consulta viaja tranquilamente dentro do corpo (body) da mensagem em formato JSON!
